## 1. What an "MCP App" actually is

An **MCP App** is a **tool + UI resource pair** that lets MCP servers deliver interactive user interfaces to MCP-enabled hosts (Claude Desktop, ChatGPT, VS Code, etc.). From plugin `CLAUDE.md` and `docs/overview.md`:

- **Server side:** A tool is registered with metadata pointing to a UI resource via `_meta.ui.resourceUri` (a `ui://` URI).
- **Host side:** When the tool is called, the host fetches the resource and renders it in a **sandboxed iframe** using `PostMessageTransport`.
- **View side:** The bundled HTML/JS (`App` class) inside the iframe communicates bidirectionally with the host using JSON-RPC over `postMessage`.

The key differentiator from "a server that exposes MCP tools" is the **UI metadata layer**. Plain MCP tools return text; MCP Apps additionally declare `_meta.ui.resourceUri`, which tells the host "I have an interactive View you can render." Spec is stable (`2026-01-26/apps.mdx`).

**Three key abstractions** (from plugin `CLAUDE.md`):
- **View** — UI running in iframe, uses `App` class + `PostMessageTransport`.
- **Host** — Chat client embedding iframe, uses `AppBridge` to proxy MCP requests.
- **Server** — MCP server that registers tools with UI metadata + resources.

**Graceful degradation:** Hosts advertise UI capability; servers check before registering UI tools. Non-UI hosts still get text fallback (`content` array).

## 2. Skills in this paradigm

**Critical finding:** The docs do NOT describe skills as being returned in tool responses. In the MCP Apps context, "skills" means **Agent Skills** (per `docs/agent-skills.md`) — instruction sets distributed via the plugin marketplace, installed once by the user's agent, then invoked via natural language ("Create an MCP App", "Add UI to my server", etc.).

**Contradiction with `workspace/alignment.md`:** Our alignment doc claims tools return skill definitions the client installs. The actual MCP Apps paradigm is:
- Four **agent skills** (`create-mcp-app`, `add-app-to-server`, `convert-web-app`, `migrate-oai-app`) are installed **once** from the plugin marketplace.
- These skills guide the AI agent through scaffolding, converting, or enriching MCP apps.
- Tools do NOT carry skill definitions; they carry `structuredContent` (data) and optionally `_meta.viewUUID` (for view state persistence).

Skills are **not** part of the tool response contract in the official spec. They're a separate Claude Code (Agent Skills) distribution mechanism.

## 3. Architectural patterns

From `docs/patterns.md`, `docs/quickstart.md`, and `examples/`:

| Pattern | Description |
|---------|-------------|
| Tools private to Apps | `visibility: ["app"]` hides tools from model; UI calls them directly (polling, pagination, chunk loading). |
| Polling for live data | App-only tool + `setInterval` on client; UI re-polls while visible. |
| Chunked data loading | App-only tool returns base64 chunks with metadata; client loops until complete. |
| Error handling | Tool returns `{ isError: true, content: [...] }`; or client uses `updateModelContext()` to inform model of runtime failures. |
| Binary resources | Tool returns `blob: base64` in resource content; client converts to data URI. |
| CSP / CORS | Server declares `_meta.ui.csp.connectDomains`, `resourceDomains`, `frameDomains` + optional `_meta.ui.domain` for CORS allowlisting. |
| Host context | Client receives theme, locale, display mode, safe area insets via `onhostcontextchanged`; uses CSS vars for styling. |
| Display modes | Client requests `requestDisplayMode({mode: "fullscreen" \| "inline" \| "pip"})`; host decides. |
| Model context updates | Client uses `updateModelContext()` to push UI state to model (e.g. current PDF page, cart contents). |
| View state persistence | Server returns `viewUUID` in `_meta`; client saves to `localStorage` using UUID as key. |
| Streaming partial input | `ontoolinputpartial` fires as LLM streams tool arguments; `ontoolinput` fires when complete. |
| Visibility-based pause | `IntersectionObserver` pauses animations / WebGL when view scrolls offscreen. |

## 4. Auth / CSP-CORS / security model

**Authorization** (`docs/authorization.md`):
- **Per-server:** Bearer token required at connection time for all requests.
- **Per-tool:** HTTP `401` returned only for protected tools; unprotected tools work without token. OAuth flow triggered on client side automatically when user calls protected tool.
- Token verified as JWT against identity provider's JWKS; servers implement `.well-known/oauth-*` discovery endpoints.
- **UI-initiated auth escalation:** Public tools load UI without auth; clicking a button calls protected tool → host triggers OAuth → tool executes with token.

**CSP** (`docs/csp-cors.md`):
- **Critical:** MCP Apps HTML runs in sandboxed iframe with **no same-origin server**. Every origin must be declared.
- Server declares in resource metadata: `connectDomains` (fetch/XHR/WebSocket), `resourceDomains` (scripts/styles/images), `frameDomains` (nested iframes).
- Optional `domain` field gives app a stable origin for APIs that require allowlisting (host-specific format, e.g. hash-based for Claude).

**Security model:** Sandboxed iframe, postMessage-only communication, declarative CSP (restrictive by default). No same-origin leaks. Hosts inspect templates during setup.

## 5. The four skills

From `plugins/mcp-apps/skills/*/SKILL.md`:

**create-mcp-app:** Scaffolds a new MCP App with interactive UI from scratch. Decision tree: framework selection (React / Vue / Svelte / Vanilla), project context (new server vs existing). Clones SDK repo, provides framework templates (6 variants), guides through tool + resource registration, build pipeline (Vite + `vite-plugin-singlefile`), handler registration (`ontoolinput`, `ontoolresult`, `onhostcontextchanged`, `onteardown` BEFORE `connect`), CSS variables for theming, testing with basic-host.

**add-app-to-server:** Enriches existing MCP server's tools with UI. Step 1: analyze which tools benefit from UI (structured data → high, text confirmations → low). Step 2: add dependencies. Step 3: Vite config. Step 4: convert tools using `registerAppTool` helper (keep `content` text fallback, add `structuredContent`). Step 5: register resources. Step 6: build View (handlers, CSS variables, optional app-only helpers for polling/chunking, CSP config, fullscreen support).

**convert-web-app:** Turns existing web app into hybrid (standalone web + MCP App). Step 1: analyze data sources (URL params, APIs, props, storage) and map to MCP equivalents. Step 2: investigate CSP requirements (trace every origin in final bundle). Step 3: set up MCP server wrapping the app. Step 4: adapt build to produce single-file MCP entry (separate from standalone build). Step 5: add hybrid detection (origin check, query param, null origin) and branch initialization (MCP mode reads from handlers, standalone mode reads from URL/APIs). Step 6: host styling (CSS variables with fallbacks).

**migrate-oai-app:** Converts OpenAI Apps SDK → MCP Apps SDK. Server-side: `_meta["openai/..."]` flat keys → `_meta.ui.*` nested structure; `text/html+skybridge` → `RESOURCE_MIME_TYPE`; snake_case CSP (`connect_domains`) → camelCase (`connectDomains`); use `registerAppTool` / `registerAppResource` helpers. Client-side: `window.openai` global → `App` instance; register handlers (`ontoolinput`, `ontoolresult`, `onhostcontextchanged`) BEFORE `connect`; sync property access → async getters/callbacks. Full mapping tables in `docs/migrate_from_openai_apps.md`.

## 6. Contradictions / refinements vs `workspace/alignment.md`

### (a) Confirmed by docs

1. **"Backend is the moat"** (alignment: "State lives in backend. Client is interchangeable.") — Confirmed. Quickstart, patterns, and examples all emphasize that tools return both `content` (text for model) and `structuredContent` (data for UI), and hosts can be swapped. Backend state is canonical.

2. **"Onboarding is a tool, not a prompt"** — *Partially confirmed.* Onboarding-as-a-tool is a valid pattern; however, the docs do NOT prescribe a specific "onboarding tool" that returns skill definitions. Instead, skills are installed once via plugin marketplace, not per-tool-response.

3. **"Minimal UI"** — Confirmed. Views are sandboxed, read-only for display, write only via tool calls. No direct database writes from UI. Pattern: `ontoolinput` receives args, `ontoolresult` receives data, UI renders read-only.

### (b) Refined / nuanced

1. **Skill distribution mechanism** (alignment claims: "tools return skill definitions; client installs them"):
   - **Docs reality:** Skills are **Agent Skills** installed once via plugin marketplace (`/plugin marketplace add modelcontextprotocol/ext-apps`), not distributed per tool call.
   - **What IS distributed in tool responses:** `structuredContent` (data), `_meta.viewUUID` (for state recovery), and optionally text `content` (fallback for non-UI hosts).
   - **Implication:** Our vision of "tool returns (data, skill update)" needs revision. Skills are managed by the plugin system, tools carry data + metadata.
   - **Citation:** `docs/agent-skills.md` § "Install the Skills" lists four skills distributed via marketplace, not via tools. Skills are invoked with natural language prompts ("Create an MCP App"), not returned by tools.

2. **"Agent-native" definition:**
   - **Docs context:** "Agent-native" in MCP Apps world means: UI is optional (graceful degradation), tools are primary, host manages display, agent makes decisions.
   - **Our alignment:** "Agent-native" emphasizes agent decision-making, removing user friction, scheduled tasks learning over time.
   - **Reconciliation:** Both meanings coexist. MCP Apps the protocol is agent-native in that tools don't require UI. Our app design is agent-native in that the agent makes the meal-planning decisions.

3. **"Tools are capabilities; skills define when/how to use them":**
   - **Docs stance:** Tools are MCP tools (exposed via server). Skills are Agent Skills (installed in user's agent environment, guide the agent's behavior).
   - **Tool visibility:** `visibility: ["app", "model"]` (default) vs `visibility: ["app"]` (UI-only, hidden from model) provides some control over agent visibility.
   - **App-only tools pattern:** This partially maps to our skill concept — tools the agent shouldn't see directly are hidden via visibility, and the UI calls them via `app.callServerTool()`.
   - **Citation:** `docs/patterns.md` § "Tools that are private to Apps" + `add-app-to-server.md` § "App-Only Helper Tools."

4. **UI minimality constraint:**
   - **Docs emphasize:** Views are sandboxed, no direct state mutation, no access to host DOM.
   - **Docs allow:** Fullscreen mode, display mode changes, host context adaptation (theme, fonts, safe area).
   - **Alignment view:** "Read in client, write only to credentials / payment." Docs are stricter: "Write via tool calls, not direct mutations." Our constraint is a *subset* of the broader sandbox constraint.

### (c) Contradicted

1. **"Tools return skill definitions":**
   - **Alignment claim:** "Each MCP-tool can return ... a skill-definition the client installs in the user's environment."
   - **Docs reality:** Tools return `content` (text), `structuredContent` (data), `_meta` (metadata like `viewUUID`). Skill definitions do NOT come from tools.
   - **Evidence:** All four `SKILL.md` files describe skills as plugin marketplace artifacts, not tool payloads. Tool responses in all examples carry data, not skill instructions.
   - **Revision needed:** Skills are separate from tools. They're installed once via `/plugin install mcp-apps@...`, then invoked by the user saying "Add UI to my MCP server" (which calls the `add-app-to-server` skill). The server's tools don't return skill definitions.

2. **Multi-client portability via tool-response skills:**
   - **Alignment claim:** "Klienten er udskiftelig ... Brugeren skifter mellem Claude og ChatGPT uden at miste sin pantry" is supported by agent-native design, BUT not via "tools returning skills."
   - **Docs reality:** Portability comes from: (a) stateless tools (server is canonical), (b) platform-agnostic protocol (MCP is standard), (c) optional UI (text fallback works everywhere).
   - **Skills are not portable this way:** ChatGPT skills ≠ Claude Code skills. If our "skill" is actually Claude-Code-specific instructions, ChatGPT users won't get it. We'd need a **separate** skill distribution mechanism per platform.
   - **Implication:** Our assumption that one tool response can distribute skills to any client is wrong. Skills are client-specific. Portability comes from backend state + text fallback, not from skills.

## 7. Open questions for the leads

1. **Skill distribution in multi-client world:** Alignment assumes tools return skill definitions to solve multi-client portability. The docs show skills are client-specific (Claude Code skills, ChatGPT custom instructions, etc.). How do we distribute platform-specific onboarding / guidance without returning it from tools? Is there a separate skill-creation mechanism, or do we embed guidance in text responses?

2. **Onboarding flow:** Currently we say "onboarding is a tool." If it's a tool, does it:
   - Return skill definitions (contradicted by docs)?
   - Return structured data + text instructions the agent reads?
   - Trigger server-side account creation and return credentials to the client?
   - All of the above?

3. **App-only tools vs visibility array:** The docs use `visibility: ["app"]` to hide tools from the model. Does this replace our skill concept, or are they complementary? If we hide a "refresh-pantry" tool from the model but keep it callable by the UI, is that a skill?

4. **CSP origins for Tjek API:** Our Tjek integration (`src/api.ts`) makes fetch requests. If we add an MCP App UI that also needs to call Tjek (for live deal data), what domains must be in `connectDomains`? Does the UI call Tjek directly, or does it call a server-side tool that calls Tjek?

5. **Payment / billing flow:** We mention "write only to credentials and payment." If payment is a tool call, who handles payment processing? The UI calls a tool → server calls Stripe / similar → returns result? Or is payment a separate out-of-band flow?

6. **Multi-user hosting model:** Currently we have `~/.tilbudstrolden.json` (single household, local). For multi-user, do we envision:
   - Each user runs their own MCP server (Docker container, local) connected to a shared payment / auth service?

   - The docs don't prescribe this; it's a design choice.

7. **Scheduled tasks:** We mention "scheduled tasks running most work automatically." MCP tools are request-response. How do scheduled tasks fit? Options:
   - Agent polls periodically (user's client periodically calls server)?
   - Separate job system outside MCP (e.g. Neon's jobs, CRON)?

8. **Image recognition:** We mention meal photo analysis as a use case. The docs don't cover file uploads (marked "Not yet implemented" in migration guide). How do we envision this working? Does the tool accept base64-encoded image data in arguments, or is there a separate resource / file API under development?

## Summary for phase 2 planning

The alignment doc is **directionally correct** but needs two key revisions before technical planning:

1. **Remove the "tools return skill definitions" assumption.** Skills come from the plugin marketplace, not tool responses. Tools carry data + metadata (`structuredContent`, `_meta.viewUUID`), not instructions.

2. **Clarify skill-distribution for multi-client.** If Claude Code skills won't work for ChatGPT users, we need a separate onboarding flow (text-only guidance in tool responses?) or accept platform lock-in.

3. **Map our "skills" concept to MCP's actual mechanisms:**
   - App-only tools (`visibility: ["app"]`) ≈ UI-only capabilities.
   - Text `content` fallback ≈ model-visible instructions.
   - `structuredContent` ≈ data the UI renders.
   - Agent Skills (from plugin marketplace) ≈ initial setup / scaffolding guidance.

The architecture remains sound: thin MCP (stateless tools), thick backend (per-user state), minimal UI (read-only, write via tools), agent-driven (decides when / how to act). We need to reframe how onboarding and multi-client support work.
