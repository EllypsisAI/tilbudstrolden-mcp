# Spec: Roadmap-station 2 — Backend domænemodel + migration fra JSON til Postgres

Status: done (2026-05-24)
Roadmap reference: [`workspace/roadmap.md` §2](../roadmap.md)

## Scope

Stand up the Postgres storage layer locked in [`decisions/db-choice.md`](../decisions/db-choice.md) and rewrite `src/store.ts` to talk to it instead of `~/.tilbudstrolden.json`. Multi-tenant from day one: schema, isolation, and connection management designed so a single shared Postgres holds many households without app-bug leakage. The existing Zod schema is the source of truth — DB shape derives from it.

Three locked design choices drive the work:

- **Toolkit:** Drizzle ORM (TypeScript-first, drizzle-zod keeps Zod ↔ DB schema in sync, lightweight runtime).
- **Tenant isolation:** Row-Level Security. Postgres enforces; app sets `app.household_id` per connection checkout. Belt and suspenders against missed WHERE clauses.
- **Nested data:** JSONB columns for small bounded embeds (`people`, `stores`, `pantry`, `recipes`). Separate tables with FK + date index for unbounded append-only logs (`mealHistory`, `spendLog`).

## Deliverables

1. **Local dev stack.** `docker-compose.yml` (or extension of existing) with a Postgres service. `README.md` (or new `docs/local-dev.md`) snippet: how to bring it up, how to run migrations, how to seed test data.
2. **Drizzle setup.**
   - `drizzle.config.ts` at repo root.
   - `src/db/schema.ts` — table declarations matching the Zod shape: `households` (one row per tenant, JSONB columns for `household` profile, `pantry`, `recipes`); `meal_log_entries` (FK `household_id`, indexed `(household_id, date desc)`); `spend_log_entries` (same pattern).
   - `src/db/migrations/0000_init.sql` — generated by `drizzle-kit`, plus RLS policies appended (or in `0001_rls.sql`) for every tenant-scoped table.
3. **Connection layer.** `src/db/client.ts` — pool config (Neon pooled URI in prod, local Postgres URI in dev, env-driven). `src/db/with-tenant.ts` — helper that wraps a unit of work, checks out a connection, runs `SET LOCAL app.household_id = $1`, executes the callback, releases. All store reads/writes go through it.
4. **Store rewrite.** `src/store.ts` keeps its public surface (same exported function signatures: `getHousehold`, `updateHousehold`, `getPantry`, `updatePantry`, `getRecipes`, `addRecipe`, `removeRecipe`, `getMealHistory`, `logMeal`, `getSpendLog`, `logSpend`, `load`, `save`, `modify`). Internally swaps file I/O + mutex for `withTenant` + Drizzle queries + DB transactions. Callers (tools in `src/tools/`) do not change.
5. **One-off JSON import script.** `scripts/import-json-store.ts` — reads a `~/.tilbudstrolden.json` (or `--file` flag), creates a household row, populates JSONB + history tables. Not wired into runtime; run once per user who has an existing local file. ~50 LOC.
6. **Tests.**
   - Existing vitest suite passes unchanged against the new backend (semantics preserved through the rewrite).
   - New test file `tests/multi-tenant-isolation.test.ts` — sets up two households, performs a read without WHERE on each, asserts each only sees its own rows. Confirms RLS is enforced even when application code "forgets" to filter.
   - Test helper: `tests/helpers/test-tenant.ts` — spins up a household, returns a context that runs callbacks with the right session var.
7. **NPM scripts.** `db:up`, `db:migrate`, `db:generate` (drizzle-kit), `db:reset`, `test:integration` (anything that needs a live DB).
8. **Alignment + roadmap sync** if execution surfaces shifts in core assumptions (probably none — this station implements decided architecture, doesn't shift it).

## Method

- **Schema-first.** Declare Drizzle tables matching the Zod shape. Generate the initial migration with `drizzle-kit generate`. Append RLS policies (`ENABLE ROW LEVEL SECURITY`, `CREATE POLICY ... USING (household_id = current_setting('app.household_id')::uuid)`) as part of the same or immediately following migration.
- **Connection scoping pattern.** A `withTenant(householdId, fn)` helper checks out a pooled connection, opens a transaction, runs `SET LOCAL app.household_id = $1`, executes the callback within the transaction, commits, and releases. `SET LOCAL` scopes the variable to the transaction — guarantees the next checkout starts clean. Single chokepoint = single audit surface.
- **Store rewrite order.** Function by function, preserving the existing public signature. Start with the read-only paths (`getHousehold`, `getPantry`, `getRecipes`), then the mutation paths, then the read-modify-write `modify` helper (which becomes a transactional Drizzle query). Each function lands with its test passing before moving on.
- **Atomicity.** The file-mutex pattern in current `store.ts` becomes a single transaction in `withTenant`. `modify(fn)` runs the callback inside the transaction so the read and the write are guaranteed consistent without app-level locking.
- **Defaults.** Default recipes (`defaultRecipes` import) get inserted into the new household's `recipes` JSONB on household creation, not on first-recipe-read. Cleaner — no implicit mutation in a read path.
- **Subagent delegation.**
  - One Explore subagent: enumerate all callers of `src/store.ts` exports across the codebase, confirm none rely on file-I/O specifics (paths, file existence, etc.) beyond the documented function contracts. Output is a confirmation or a list of leaks.
  - One implementation subagent (or two parallel) once the connection helper exists: rewrite store functions in batches, each verified against existing tests before merging.
  - Code-review subagent on the final diff before commit.

## Open questions delivered to station 3 (auth)

- **`household_id` provenance in request lifecycle.** Auth will supply it via token claims; the middleware between auth and DB sets `app.household_id`. For station 2 we hard-code or env-supply.
- **Service-role bypass.** Some operations (a future cron job that aggregates across households for billing) need to escape RLS. Pattern: separate Postgres role for the service that has `BYPASSRLS`, distinct from the per-request role. Out of scope here but worth flagging.

## Open questions delivered to station 4 (deploy)

- **Neon connection mode.** Pooled URI (PgBouncer in transaction-mode) vs direct connection. Pooled is the default for serverless compute; direct is required for `LISTEN/NOTIFY` and some session-level features. We use neither of those yet, so pooled is fine. Confirm at deploy.
- **Pool sizing.** Connections-per-tenant vs flat pool. Depends on compute provider's concurrency model.
- **Connection-string secret management.** Whatever secrets-manager the deploy target uses.

## Open questions surfaced during execution (resolve in-flight, document in decisions/ if material)

- **Drizzle migration metadata location.** Defaults to a `_drizzle_migrations` table — fine. Confirm prod-branch RLS doesn't accidentally apply to it.
- **`updateHousehold` partial-update semantics.** Current implementation does a shallow merge. With JSONB column we have a choice: read-merge-write the whole JSONB, or use Postgres `jsonb_set`. Latter is atomic and avoids lost-update under concurrency; former is simpler. Pick during rewrite; flag if non-trivial.
- **`getRecipes` country-seeding logic.** Current behavior seeds Danish defaults on first read for DK households. Moving this to household-creation time (per Method above) changes the trigger. Confirm no test relies on the lazy-seed behavior.
