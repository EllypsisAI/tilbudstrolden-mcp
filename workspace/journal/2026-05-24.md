## [station-2] Backend domænemodel + migration fra JSON → Postgres: done

**Co-write af spec:**

- 3 lock-decisions truffet før spec'en blev draftet: **Drizzle ORM på Node** (TypeScript-first, `drizzle-zod` keeps Zod canonical, Neon-anbefalet, runtime-portable), **Row-Level Security** (DB enforcer pr-husstand-isolation), **JSONB for bounded embeds** (people, stores, pantry, recipes) med separate tabeller for unbounded append-only logs (meal_log_entries, spend_log_entries).
- Bun-spørgsmål adresseret som distinct fra ORM-valget: Drizzle og Bun lever på forskellige lag. Bun-spørgsmålet (runtime) skubbet til station 4 (compute-provider). Drizzle valgt fordi den er portable på tværs af runtime.
- Spec'en committet til `workspace/specs/02-backend-domain-and-migration.md` (`56bf472`).

**Eksekvering — alle deliverables grønne:**

- **Lokal dev-stack:** `docker-compose.yml` + `scripts/db-up.sh` med Docker-first / system-Postgres-fallback (Docker er det forventede path på dev-maskinen; fallback gør cloud-sessioner self-sufficient). `scripts/db-down.sh` med `--volumes` flag til destructive teardown.
- **Drizzle-setup:** `drizzle.config.ts`, `src/db/schema.ts` (households + meal_log_entries + spend_log_entries), `src/db/migrations/0000_initial.sql` (hand-authored så RLS-policies sidder ved siden af tables de beskytter — drizzle-kit autogen forstår ikke RLS).
- **Connection-layer:** `src/db/client.ts` (pool), `src/db/with-tenant.ts` (chokepoint: `set_config('app.household_id', ..., true)` inde i transaktion), `withoutTenant` escape hatch for migrator/import-script. `src/db/migrate.ts` (60-line runner med `_migrations` ledger). `src/db/env.ts` loader til `.env.local`. `src/db/bootstrap.ts` (idempotent: genererer `TILBUDSTROLDEN_HOUSEHOLD_ID` hvis manglende, opretter household-row hvis manglende, seeder default-DK-opskrifter på creation tid — flytter væk fra legacy lazy-seed-i-getRecipes).
- **Store-rewrite:** `src/store.ts` rewrite preserver alle 18 tool-callsites uændret. Public surface (`getHousehold`, `updateHousehold`, `getPantry`, `updatePantry`, `getRecipes`, `addRecipe`, `removeRecipe`, `getMealHistory`, `logMeal`, `getSpendLog`, `logSpend`) bevarer signaturer. `load/save/modify` (interne file-mutex-primitiver fra JSON-æraen) dropped — server.ts brugte dem ikke. Read-modify-write atomicitet er nu DB-niveau transaction i stedet for fil-mutex.
- **One-off importer:** `scripts/import-json-store.ts` migrerer legacy `~/.tilbudstrolden.json` til en household-row + per-table logs. CLI: `--file`, `--household`, `--force`. Verificeret end-to-end mod sample-fil.
- **Tests:** 
  - 11 live CRUD-tests i `src/db/store.live.test.ts` mod ægte Postgres — verificerer at alle 11 public-store-funktioner round-trippter korrekt med RLS i mellem.
  - 4 RLS-isolation-tests i `src/db/isolation.live.test.ts` — to husstande A+B skriver data via public store API, læser, asserts cross-tenant ingen leakage. "Raw connection uden session var → 0 rows" som negativ-kontrol. Targeting B's id mens A's session var er sat → også 0 rows (USING clause stronger than WHERE).
  - 227 eksisterende pure-function tests bestod uændret — semantikken bevaret gennem rewrite. Total: **242 tests passing**.
- **NPM scripts:** `db:up`, `db:down`, `db:reset`, `db:migrate`, `db:bootstrap`, `db:generate`, `db:import-json`, `setup` (chain: up → migrate → bootstrap).
- **Docs:** README "Quick start" opdateret med Postgres-setup. CLAUDE.md "Repo facts" opdateret — fjerner "state er JSON-fil"-misinformation, peger på `src/db/schema.ts` + `withTenant` som source-of-truth.

**I forbifarten besluttet:**

- **Default-recipe seeding flyttet** fra lazy `getRecipes()`-mutation (legacy) til `bootstrap.ts` ved household-creation. Cleaner: reads er nu read-only. Tradeoff: hvis recipes wipes, ingen auto-reseed — det er fint, det er ikke et flow vi designer for.
- **FORCE ROW LEVEL SECURITY** valgt eksplicit (ikke kun ENABLE). Postgres exempter table owner fra RLS by default; FORCE gør policies binding på alle, inkluderende owner. Belt-and-suspenders fordi vi connecter som DB owner i dev — uden FORCE ville vores tests pass selv hvis RLS var broken.
- **`NULLIF(current_setting(...), '')::uuid`** i RLS-predikater i stedet for ren `current_setting(...)::uuid`. set_config med `true` returnerer tom-streng (ikke NULL) når sat eksplicit til "", og UUID-cast på "" raiser. NULLIF normalize det til NULL, hvilket fejler equality-check stille — præcis adfærden vi vil have.
- **`withoutTenant`** dokumenteret som escape hatch kun til migrator + importer + future cross-tenant cron. Står som åbent for station 4 deploy: provision en dedikeret `BYPASSRLS`-role for service-operations i stedet for at læne på "uden tenant-context returnerer RLS 0 rows."
- **Service-role-håndtering** og **connection pool sizing** eksplicit udskudt til station 4. Open questions doc'et i spec.
- **Docker-fail-fast:** scripts/db-up.sh tjekker `docker info` før den prøver `docker compose up`. Undgår 60-sekunders ventetid i environments hvor CLI'en findes men daemonen ikke kører.

## [auth-provider] WorkOS valgt som auth-provider; EU-data-residency anerkendt som åbent koncern med eksplicitte revisit-triggers

**Skete:**

- User flagged auth som næste konkrete spørgsmål — Google + Microsoft social login, OAuth ikke API-keys, leaner mod managed service efter en dev-ven's anbefaling.
- Spawned Sonnet research-subagent til at evaluere managed + self-hosted OAuth-providers mod MCP 2025-03-26 spec (DCR, CIMD, PKCE, social federation). 25 min research, 9 services vurderet med doc-citationer.
- Decision narrowed to WorkOS AuthKit vs Better Auth vs Descope. User valgte at **gå med WorkOS** og log EU-data-residency som åbent issue for senere — pragmatisk valg for DM-launch hvor speed-to-launch + 1M MAU free tier vejer tungere end EU-hosting ved nuværende skala.
- **`decisions/auth-provider.md` skrevet** med fuld tradeoff-analyse, eksplicit "revisit triggers"-sektion (≥100 DAU, Schrems III, WorkOS-pricing-shift, WorkOS-acquisition, regulated-industry customer, WorkOS shipper EU region) der gør det operationelt klart hvornår vi skal genåbne beslutningen.

**I forbifarten besluttet (allerede i decision-recorden, men værd at fremhæve):**

- **`sub` → `household_id`-mapping via en `users` tabel** gør auth-provider-skiftet billigt senere. WorkOS' subject ID er kun fremmednøgle i en mapping-tabel; faktisk app-data hænger på `household_id`. Migration til Descope eller Better Auth = re-link sub'erne, ingen data-flytning.
- **App-data forbliver i EU** uanset auth-provider — Neon Postgres kan provisiones i Frankfurt/Stockholm. Kun email + provider-sub flyver til WorkOS US. Det er den ærlige scope af EU-data-issuet, ikke "alle bruger-data går til USA".
- **MCP-clients (Claude Desktop, ChatGPT, Cursor) auto-registrerer sig via DCR + CIMD** når de kobler til vores server. Ingen manuel client_id-administration per klient.

**Åbent / næste session:**

Næste session: write `workspace/specs/03-auth-and-multi-user-identity.md` med WorkOS som locked baseline. Skal dække: WorkOS-konto + dashboard-setup, `users`-tabel migration, JWT-validation middleware, request-context-injection så `app.household_id` sættes pr. tool-kald, ny-bruger onboarding (første gang vi ser en sub → create household), MCP-server's HTTP transport switch (vi er stadig stdio i station 2 — auth-spec'en kræver HTTP).
